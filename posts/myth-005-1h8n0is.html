1972 년 청문회 기록의 총 페이지 수는 3,482 장이었지만, 실제 코드화된 정보는 3,105 장에 불과했다. 그 차이로 인해 남은 377 장은 '서브프로젝트 A-42'와 같은 분류를 가진 민감한 데이터가 숨겨진 영역으로 추정된다. 이 숫자는 단순한 우연이 아니라, 당시 정보 처리 시스템의 한계를 보여주는 지표다.

서브프로젝트 코드 확인 및 세션 타임아웃 분석

내부 분석관들은 코드를 확인하는 방식이 지금의 인터페이스 로그와 유사하다고 여겼다. 예를 들어, '서브프로젝트 B-7'은 1972 년 3 월에 중단되었는데, 이는 하드웨어 과부하로 인한 '세션 타임아웃'과 동종 구조였다. 만약 페이지 번호를 정확히 따라가면 실패 원인을 추적할 수 있다. 특히 버전 관리 기록을 보면 초기 모델의 데이터 손실률이 급격히 높게 나타나는데, 이는 인터페이스 설계 오류에서 기인한 경우가 많다.

이 때 가장 흥미로운 건 '상암 코인노래방 후기'에서 언급되는 기계의 내구성과 연결된다. 당시 장비는 특정 조건에서 재부팅 후 데이터 소실을 겪었는데, 이는 코인노래방이 한 명의 사용자 세션 동안 소비하는 전력량과 유사하다. 사용자가 세션 시간을 충분히 확보하지 못하면 하드웨어가 최적 상태로 작동하기 전에 오류를 발생시키는 패턴을 보이다 보니 결과적으로 데이터 품질이 저하된다. 즉, 입력 장치가 끊어지면 출력의 연속성이 깨지는 구조다.

실패 원인 비교 분석: 오류 코드 88
